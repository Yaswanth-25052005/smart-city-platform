## Part A: Executive Summary

### 1. Project Objective & Problem Statement
Modern urban agglomerations face unprecedented challenges in environmental monitoring, traffic and parking management, public safety, and energy conservation. The **Smart City Big Data Analytics Platform** was designed to address these challenges by providing a scalable, real-time distributed data pipeline that ingests IoT telemetry, streams events with high throughput and low latency, persists historical data reliably, computes distributed aggregations using big data engines, detects threshold anomalies in real time, generates machine learning predictive forecasts, and delivers actionable visualizations through a unified dashboard.

### 2. Main Technologies Employed
- **Programming Language:** Python 3.11 / 3.12
- **Data Validation & Modeling:** Pydantic v2 (`BaseModel`, `Field`, `ConfigDict`)
- **Event Streaming & Buffering:** Apache Kafka 7.5.0 (Confluent Platform) + Apache Zookeeper
- **Primary Data Storage:** MongoDB Community Server 7.0 + Mongo Express Admin UI
- **Big Data Analytics:** Apache Spark 3.5.3 (PySpark in containerized local[*] cluster mode)
- **Machine Learning:** Scikit-learn (Random Forest Classifier for parking occupancy, Random Forest Regressor for AQI prediction), Joblib
- **REST Backend:** FastAPI 0.116.1 + Uvicorn ASGI Server
- **Interactive Visualization:** Streamlit 1.48.1 + Plotly Express 6.3.0
- **Container Infrastructure:** Docker Desktop + Docker Compose v2

### 3. Current Implementation Status
The core platform architecture is fully operational inside a multi-container Docker deployment. Real-time telemetry is actively generated by a virtual IoT simulator representing two dedicated hardware profiles:
1. `ESP32_ENV_01`: Temperature (DHT22), Humidity (DHT22), Air Quality (MQ135), Noise (MAX4466).
2. `ESP32_TRAFFIC_01`: Parking occupancy (HC-SR04 ultrasonic sensor) and Smart Streetlighting (IR sensor / circadian schedule).

Data streams through Kafka topic `smartcity.sensor_data`, is validated against the `SensorEvent` schema, and is persisted to MongoDB collection `sensor_data` by an asynchronous ingestion consumer. A FastAPI REST API serves platform health, latest and historical sensor readings, active alerts, Spark analytics aggregations, and device/location summaries to a multi-page Streamlit dashboard.

### 4. Key Technical Accomplishments
1. **Strict Data Contract & Ingestion Decoupling:** Implemented a single authoritative Pydantic contract (`SensorEvent`) that enforces UUID validation, ISO 8601 timestamps, device identity, and nullable fields, isolating downstream components from hardware differences.
2. **Device Identity Isolation:** Built explicit query filtering (`ACTIVE_DEVICES = ["ESP32_ENV_01", "ESP32_TRAFFIC_01"]`) across the repository and service layers, eliminating legacy simulator noise and ensuring clean analytics.
3. **Stateful Alert Deduplication & Auto-Resolution:** Designed an alert engine that prevents duplicate alerts for ongoing conditions and automatically marks active alerts as `RESOLVED` when sensor readings return to safe thresholds.
4. **End-to-End Containerization:** Created Dockerfiles and a unified `docker-compose.yml` with health checks and startup dependencies, requiring no host Java or manual Spark configuration.
5. **Interactive 10-Page Dashboard:** Deployed a modular Streamlit UI covering environmental monitoring, air quality, noise, smart parking, street lighting, alert management, analytics, device tracking, location rollups, and ML forecasts.

### 5. Outstanding Limitations & Gap Analysis
1. **MQTT Broker & Bridge Not Implemented:** Physical ESP32 devices communicate via MQTT, but the current implementation publishes directly from the simulator to Kafka via `kafka-python`. An MQTT broker (e.g., Eclipse Mosquitto) and an MQTT-to-Kafka consumer/bridge service must be added before physical microcontrollers can be deployed.
2. **Spark Pipeline Scheduling:** The Spark container runs a heartbeat daemon (`spark_daemon.py`), and the analytical transformation/aggregation logic exists in `backend/spark/pipeline.py`, but it is not scheduled on a recurring cron or streaming trigger inside Compose.
3. **Double-Prefix Route Bug in Predictions API:** `backend/api/routes/predictions.py` defines `prefix="/api/predictions"` and is registered in `backend/api/main.py` with `prefix="/api/predictions"`, exposing the endpoints at `/api/predictions/api/predictions/latest`. As a result, calls from the dashboard to `/api/predictions/latest` return 404 Not Found.
4. **Streamlit UI Schema Key Mismatches:** Dashboard pages `8_Devices.py` and `9_Locations.py` expect dictionary keys `last_seen`, `latest_readings`, and `active_devices`, whereas the FastAPI backend models return `latest_timestamp`, `latest_status`, and `devices`.
5. **ML Ingestion Loop:** While models are trained and saved as joblib artifacts, inference (`predict.py`) is executed manually rather than as an automated scheduled worker.

### Layered Responsibilities
1. **Perception & Acquisition Layer:** Simulates or reads physical hardware sensors and produces standardized JSON events.
2. **Transport & Ingestion Layer:** Uses Kafka as a high-throughput, fault-tolerant message buffer; consumer enforces schema validation before persistence.
3. **Persistence Layer:** MongoDB stores semi-structured sensor records, indexing on timestamps, device IDs, and location IDs.
4. **Analytics & Intelligence Layer:** Spark cleans and aggregates data into hourly statistical summaries; Scikit-learn models predict short-term parking occupancy and air quality.
5. **Application & Service Layer:** FastAPI acts as an API gateway, enforcing business rules and preventing direct database coupling from the presentation layer.
6. **Presentation Layer:** Streamlit queries the REST API, rendering interactive Plotly charts, real-time KPI metrics, and operational tables.

## Part E: Data and Database Design

### 1. Authoritative SensorEvent Data Contract
Every telemetry record passing through Kafka into MongoDB must adhere to the Pydantic `SensorEvent` schema defined in [`backend/domain/sensor.py`](file:///c:/Users/yaswa/OneDrive/Documents/smart-city-platform/backend/domain/sensor.py):

```python
class SensorEvent(BaseModel):
    event_id: UUID4
    device_id: str
    location_id: str
    timestamp: datetime
    
    # Environmental telemetry (ESP32_ENV_01)
    temperature: Optional[float] = None
    humidity: Optional[float] = None
    air_quality: Optional[float] = None
    noise: Optional[float] = None
    
    # Traffic & municipal telemetry (ESP32_TRAFFIC_01)
    parking_occupied: Optional[bool] = None
    streetlight_on: Optional[bool] = None
```

#### Validation Rules & Data Handling
- **UUID Validation:** `event_id` must be a valid RFC 4122 UUID4. Invalid strings cause validation failure and rejection.
- **Timestamp ISO 8601:** `timestamp` is parsed by Pydantic into a timezone-aware UTC datetime.
- **Nullable Fields:** Physical separation between sensor profiles is respected. Environmental fields are `None` (JSON `null`) for traffic nodes, and traffic fields are `None` for environmental nodes.
- **Physical Bounds Enforced:** Spark cleaning (`cleaning.py`) drops records with temperatures outside `[-50°C, 60°C]`, humidity outside `[0%, 100%]`, or negative air quality/noise values.

### 2. MongoDB Database & Collection Architecture
**Database Name:** `smart_city` (configured via `MONGO_DATABASE` / `DATABASE_NAME`).

| Collection Name | Write Producers | Read Consumers | Primary Indexes | Retention / Cleanup |
| :--- | :--- | :--- | :--- | :--- |
| `sensor_data` | `consumer_runner.py` | FastAPI (`SensorService`), Spark Loader, ML Loader | `timestamp` (DESC), `device_id` (ASC) | Append-only raw event log |
| `alerts` | `alert_engine.py`, `alert_service.py` | FastAPI (`AlertService`), Streamlit Alert Center | `alert_id` (Unique), `status`, `location_id`, `timestamp` | Stateful (Active/Resolved) |
| `analytics` | Spark Pipeline (`writer.py`) | FastAPI (`AnalyticsService`), Streamlit Analytics | `_id` (`{metric}_{location}_{date}_{hour}`) | Upsert mode (`operationType=replace`) |
| `predictions` | ML Predict (`predict.py`) | FastAPI (`PredictionService`), Streamlit Predictions | `prediction_id` (Unique), `prediction_type`, `device_id` | Historical log of forecasts |

## Part F: Messaging and Big Data Processing

### 1. Messaging & Streaming Analysis
- **Kafka Broker:** Confluent Kafka 7.5.0 operating on port `9092` (host access) and `29092` (internal Docker bridge network).
- **Topic Configuration:**
  - `smartcity.sensor_data`: Main telemetry stream, 1 partition, replication factor 1.
  - `smartcity.alerts`: Reserved for alert events.
  - `smartcity.analytics`: Reserved for analytical streaming events.
- **Consumer Group:** `smart-city-ingestion` runs with `auto_offset_reset="latest"` and `enable_auto_commit=True`. In production, offset committing ensures at-least-once delivery semantics.
- **MQTT Status:** The intended architecture assumes physical microcontrollers publish to MQTT. Currently, the simulator bypasses MQTT and publishes directly to Kafka. An MQTT broker and an MQTT-to-Kafka bridge are required for physical ESP32 integration.

### 2. Spark Analytics Implementation
- **Session Architecture:** PySpark 3.5.3 running in Docker with `master("local[*]")`. Communicates with MongoDB using the official `mongo-spark-connector_2.12:10.3.0`.
- **Cleaning Stage (`cleaning.py`):**
  1. Drops rows with null `event_id`, `location_id`, or `timestamp`.
  2. Drops duplicate records matching existing `event_id`s.
  3. Casts strings to Spark `TimestampType`.
  4. Filters out out-of-range sensor values.
- **Transformation Stage (`transformations.py`):**
  1. Extracts calendar `date` (`yyyy-MM-dd`), integer `hour` (`0–23`), and `day_of_week`.
  2. Casts boolean fields (`parking_occupied`, `streetlight_on`) to numeric `0/1` integers.
- **Aggregation Stage (`aggregations.py`):**
  Computes group-by aggregations over `[location_id, date, hour]` for:
  - Temperature: `avg`, `min`, `max`, `count`
  - Humidity: `avg`, `min`, `max`, `count`
  - Air Quality: `avg`, `min`, `max`, `count`
  - Noise: `avg`, `min`, `max`, `count`
  - Parking Occupancy: `avg` (percentage occupancy), `min`, `max`, `count`
  - Streetlight Status: `avg` (percentage active), `min`, `max`, `count`
- **Output:** Unions all metric dataframes into a standardized schema and writes to MongoDB collection `analytics` with replace/upsert semantics.

## Part G: Machine Learning and Alert Engine

### 1. Alert Engine & Stateful Deduplication
The alert engine (`backend/services/alert_engine.py` & `alert_service.py`) processes both real-time device records and aggregated analytics:
- **Threshold Rules:**
  - High Temperature: Reading > 45.0°C (Severity: MEDIUM, or HIGH if > 50°C).
  - Extreme Temperature Anomaly: Reading < -20.0°C or > 60.0°C (Severity: LOW).
  - High Noise: Reading > 80.0 dB (Severity: MEDIUM).
  - Poor Air Quality: Aggregated AQI > 150.0 (Severity: HIGH, or CRITICAL if > 200.0).
  - Parking Congestion: Aggregated occupancy > 90.0% (Severity: HIGH).
  - Streetlight Anomaly: Streetlight reported OFF when expected ON (Severity: LOW).
- **Stateful Lifecycle Management:**
  - If a threshold is exceeded and NO active alert exists: creates a new `ACTIVE` alert.
  - If a threshold is exceeded and an active alert ALREADY exists: suppresses duplicate creation.
  - If a reading returns to normal: automatically marks the existing active alert as `RESOLVED`.

### 2. Machine Learning Models
- **Smart Parking Occupancy Model:**
  - **Algorithm:** `RandomForestClassifier(n_estimators=50, max_depth=5, random_state=42)`
  - **Input Features:** `['hour', 'day_of_week', 'recent_occupancy_mean']`
  - **Target Variable:** Binary parking occupancy state at $T+60\text{s}$ (shifted 20 steps).
  - **Metrics Evaluated:** Accuracy, Precision, Recall, F1-Score.
  - **Output:** Predicted occupancy probability (`predict_proba`) stored in MongoDB `predictions`.
- **Air Quality Forecasting Model:**
  - **Algorithm:** `RandomForestRegressor(n_estimators=50, max_depth=5, random_state=42)`
  - **Input Features:** `['hour', 'temperature', 'humidity', 'recent_aqi_mean']`
  - **Target Variable:** Continuous air quality value at $T+60\text{s}$ (shifted 20 steps).
  - **Metrics Evaluated:** MAE (Mean Absolute Error), RMSE (Root Mean Squared Error), $R^2$ Score.
  - **Output:** Predicted future AQI metric stored in MongoDB `predictions`.
- **Trained Artifacts:** Serialized in `backend/ml/models/parking_model.joblib` and `air_quality_model.joblib`.

   - *Impact:* Route is registered at `/api/predictions/api/predictions` instead of `/api/predictions`.

   - *Impact:* Spark aggregations do not run automatically unless invoked.
   - *Fix:* Add an hourly cron or background task to trigger `backend/spark/pipeline.py` within the Spark container.

   - *Impact:* Forecasts are only updated when `predict.py` is executed manually.
   - *Fix:* Create a background daemon or scheduled service to execute `predict.py` every 60 seconds when `ML_ENABLED=true`.
